# 000. Подготовка запускаемого приложения

## Цель

Подготовить минимальное локальное desktop-приложение myInvest на Go + Wails +
Svelte/TypeScript с SQLite и механизмом миграций. Это техническая предпосылка
для [справочника валют](001-currency-directory.md) и следующих бизнес-фич.

## Требования

- Выбрать совместимые версии Go, Wails, Svelte/TypeScript и инструментов сборки.
  Зафиксировать версии, зависимости и lock-файлы в репозитории; значимые решения
  и выбор SQLite-драйвера описать в `docs/decisions/`.
- Создать Go-модуль, точку входа Wails и минимальный Svelte-интерфейс.
  Приложение открывает главное окно с названием myInvest.
- Обеспечить проверяемую связь UI с Go через небольшой технический вызов,
  например получение названия приложения. Wails остаётся тонким адаптером.
- Подключить SQLite через слой хранения. По умолчанию база располагается рядом
  с приложением; точный путь документируется. При первом запуске
  каталог и база создаются автоматически, при повторном используются существующие.
- По умолчанию использовать переносимый режим: `myinvest.sqlite3` рядом
  с `.app` на macOS или рядом с отдельным бинарником на любой платформе.
  `MYINVEST_DATA_DIR` имеет приоритет; отсутствие `MYINVEST_PORTABLE`, пустое
  значение и `1` выбирают переносимый каталог. Только явное `0` выбирает
  прежний системный каталог. Иные значения вызывают понятную ошибку.
  Используется фактический путь бинарника после разрешения символических ссылок.
  Данные автоматически не переносятся; ошибка записи не меняет выбранный каталог.
- Включать внешние ключи для каждого соединения. Закрывать соединения при
  завершении приложения. Ошибки открытия БД и миграций показывать понятным
  сообщением; не продолжать работу с неподготовленной БД.
- Подготовить запуск последовательных версионированных SQL-миграций из
  `migrations/` и учёт применённых версий. Файлы миграций доступны также
  в собранном приложении. Применённые миграции не запускаются повторно.
- Каждая миграция и запись её версии применяются атомарно. При ошибке изменения
  этой миграции откатываются, её версия не помечается применённой.
- Перед применением новых миграций к существующей БД создавать согласованную
  резервную копию средствами, учитывающими SQLite-журнал. При ошибке создания
  копии миграции не запускать. Пользовательская БД не удаляется и не сбрасывается.
- Документировать в README требования к среде, установку зависимостей, запуск
  разработки, сборку и проверки. Указать проверенную ОС и ограничения платформ.

## Границы задачи

В эту задачу входят оболочка приложения, жизненный цикл SQLite, механизм миграций
и команды проверки. Бизнес-таблицы, начальные USD/RUB, курсы и окно их ввода
реализуются по спецификации 001. Для проверки миграций используются временные
тестовые БД и тестовые миграции; фиктивные бизнес-таблицы не нужны.

Apache ECharts остаётся частью выбранного стека, но подключается при появлении
фичи с графиками. Пустые бизнес-модули и дополнительные инфраструктурные слои
заранее не создаются. Финансовое представление курсов выбирается в рамках фичи 001.

## Критерии приёмки

1. Из чистого checkout после установки описанных зависимостей запускается
   desktop-окно myInvest; UI успешно вызывает Go через Wails.
2. Сборка создаёт запускаемое приложение, которому не нужен исходный каталог
   для доступа к миграциям и ресурсам интерфейса.
3. Первый запуск без переменных окружения создаёт `myinvest.sqlite3` рядом
   с приложением; повторный запуск сохраняет её данные.
4. На временной SQLite-БД проверены порядок миграций, отсутствие повторного
   применения, откат при ошибке и ограничения внешних ключей.
5. Обновление существующей тестовой БД создаёт читаемую резервную копию;
   ошибка резервного копирования предотвращает запуск новых миграций.
6. Ошибки инициализации БД и миграций не приводят к удалению данных или
   запуску приложения с неготовым хранилищем.
7. Выполнены `gofmt`, `go test ./...`, `go vet ./...`, проверка TypeScript/Svelte
   и сборка фронтенда по реально созданным скриптам `package.json`.
   README содержит команды, которыми результат был проверен.
8. Проверены переносимый режим по умолчанию (в том числе пустая переменная),
   независимость от cwd, приоритет явного каталога, явное отключение режима,
   размещение БД вне macOS-пакета, путь отдельного бинарника, сохранение переносимой
   тестовой БД при повторном открытии и корректный SQLite URI с буквой Windows-диска.

## Порядок работы

1. Выбрать версии и драйвер SQLite, зафиксировать решения в ADR.
2. Инициализировать Go/Wails/Svelte и проверить связь UI с Go.
3. Реализовать открытие и закрытие SQLite, резервное копирование и миграции.
4. Добавить интеграционные тесты на временных БД, проверить запуск и сборку.
5. Обновить README и `docs/architecture.md` по фактической реализации.
