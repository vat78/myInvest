# ADR 0007: общий журнал операций с отдельными таблицами деталей

Статус: принято. Дата: 2026-10-13.

## Контекст

Фича 003 хранит пополнения и выводы в `cash_flows`. Фича 004 добавляет сделки,
которые должны отображаться в том же журнале и участвовать в общем расчёте
денежного баланса. Нужны единые идентификаторы и устойчивый порядок внутри дня.
Наборы данных денежных операций и сделок различаются.

## Решение

Использовать общую таблицу `operations` и две таблицы деталей:

- `operations`: ID, портфель, календарная дата, тип, комментарий.
- `cash_flow_details`: ID операции, исходная валюта, исходная сумма,
  фактическая сумма в валюте портфеля.
- `trade_details`: ID операции, актив, количество, сумма сделки,
  дополнительные расходы, средняя цена.

Тип в `operations` различает пополнение, вывод, покупку и продажу.
`operation_id` таблиц деталей — одновременно первичный и внешний ключ
на `operations.id`; удаление родителя каскадно удаляет детали.
Каждая операция имеет ровно один набор деталей, соответствующий её виду.
Ограничения БД должны исключать детали чужого вида; конкретный механизм
закрепляется при реализации миграции. Первичный и внешний ключи сами по себе
не гарантируют наличие деталей: сценарий создаёт родителя и нужные детали
в одной транзакции, а чтение не выдаёт неполную запись за корректную операцию.

Направление можно изменить внутри вида: пополнение ↔ вывод, покупка ↔ продажа.
Преобразование денежной операции в сделку и обратно не поддерживается.
Портфель и ID при редактировании не меняются.

Общий ID устойчив и не переиспользуется после удаления; SQLite использует
INTEGER PRIMARY KEY AUTOINCREMENT. DTO передают ID строками.
Порядок отображения — дата DESC, ID DESC; порядок исторических проверок —
дата ASC, ID ASC. Это технический порядок, а не время биржевого исполнения.

Новая миграция атомарно переносит существующие `cash_flows` в общую таблицу
и денежные детали, сохраняя идентификаторы и все исходные данные. Новые ID
выделяются выше максимального перенесённого. После перехода прежняя таблица
не используется как второй источник истории. Применённые миграции остаются
неизменными; перед миграцией существующей БД выполняется резервная копия.

Вся запись операции и её деталей атомарна. Когда будет реализовано сохранение
производных остатков, их пересчёт входит в ту же транзакцию. Финансовые значения
остаются точными строками TEXT; общая структура не меняет правил арифметики.

## Альтернативы

Одна таблица с nullable-полями проще для чтения, но требует множества условных
ограничений и расширения общего набора колонок при появлении новых видов.

Независимые таблицы денежных операций и сделок сохраняют прежнюю структуру,
но требуют дополнительного механизма общих ID и порядка журнала.

## Последствия

Общие данные и порядок задаются одним источником. Новые виды операций могут
получать собственные таблицы деталей. Чтение требует JOIN, а запись — транзакции
и явного обеспечения соответствия типа и деталей.

Этот ADR фиксирует только структуру операций. Правила точности средней цены,
сохранения дневных остатков и исторических предупреждений остаются предложениями
спецификации 004 и требуют отдельного согласования.
