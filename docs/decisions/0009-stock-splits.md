# ADR 0009: split в общем журнале и точный пересчёт количества

Статус: принято и реализовано.
Дата: 2026-10-13.

## Контекст

[ADR 0007](0007-unified-operations.md) задаёт общие операции и отдельные детали
для денежных операций и сделок. Split преобразует существующее количество,
не меняя деньги. Порядок только по ID недостаточен: добавленный задним числом
split должен предшествовать сделкам своей даты. Деление количества может
вывести результат за пределы точных конечных десятичных строк.

## Решение

Используется общий тип `split` с деталями `split_details`: операция, актив,
положительные целые `old_units` и `new_units`, хранимые и передаваемые строками.
Прямой и обратный split используют одну формулу и один набор деталей.
Сохраняются гарантии идентичности, соответствия вида деталей и транзакционной
записи ADR 0007. Исходные сделки не переписываются.

Согласованный порядок расчёта: дата ASC, split перед остальными операциями,
затем ID ASC внутри группы. Журнал также показывает split первым внутри дня,
сохраняя даты DESC и ID DESC внутри групп. Это уточняет порядок ADR 0007
для новой фичи; порядок денежных операций и сделок между собой не меняется.

Количество вычисляется точно в Go: Q × new_units / old_units. После сокращения
знаменателя допустимы только множители 2 и 5. При ином знаменателе изменение
отклоняется без округления. Ошибка любого split в затронутой истории откатывает
всю запись или удаление вместе с производными остатками. Конечные дроби
сохраняются как точный TEXT; рациональный формат постоянного хранения не вводится.
Компенсация дробных акций и округление до целых в эту версию не входят.

## Альтернативы и последствия

Хранить split как покупку/продажу неудобно: он преобразует остаток,
а не задаёт фиксированное добавление/списание, и не имеет суммы исполнения.
Отдельные типы прямого и обратного split дублируют одинаковые правила.

Рациональное хранение количества позволило бы поддержать любые пропорции,
но потребовало бы изменения DTO, хранения и отображения всех остатков.
Округление количества нарушило бы согласованную точность. Поэтому пока
поддерживаются только точные конечные десятичные результаты.

Пересчёт должен проверять конечность до форматирования строки; существующее
преобразование, рассчитанное только на конечные десятичные числа, нельзя
применять к произвольной рациональной дроби без проверки. Поздняя правка
истории может быть отклонена из-за последующего split, с явным объяснением.
Подробные правила и критерии — в [спецификации 005](../features/005-stock-splits.md).
