# ADR 0017: хранение целевого распределения портфеля

Статус: принято запросом на реализацию. Дата: 2026-10-14.

## Контекст

Целевые доли принадлежат конкретному портфелю и должны переживать изменение
остатков, пополнения, сделки и split. Текущие количества и цены уже выводятся
из истории; хранение рассчитанных рекомендаций создаст второй источник истины.
Требования и открытые вопросы — в [фиче 010](../features/010-portfolio-target-allocation.md).

## Решение

Один текущий план на портфель, без календарной истории стратегий.
Нормализованное хранение в двух STRICT-таблицах миграции 0011:

| Таблица | Поля и ограничения |
|---|---|
| portfolio_allocation_plans | portfolio_id: INTEGER PK/FK → portfolios; generation: TEXT NOT NULL, уникальный токен создания; revision: INTEGER NOT NULL, положительная версия; cash_weight_units: INTEGER NOT NULL CHECK от 0 до 10000 |
| portfolio_allocation_targets | portfolio_id: FK → план ON DELETE CASCADE; asset_id: FK → assets; weight_units: INTEGER NOT NULL CHECK от 0 до 10000; PK(portfolio_id, asset_id) |

Строка плана отличает отсутствие цели от наличия конфигурации и обеспечивает
проверку версии при замене/удалении. Создание проверяет отсутствие плана,
замена и удаление проверяют ожидаемые generation и revision в той же write-транзакции.
Конкурирующие изменения завершаются явным конфликтом без перезаписи чужих данных.
При удалении и повторном создании генерируется новый generation, чтобы старый
запрос с совпавшим номером revision не мог изменить заново созданный план.
Токен создаётся в Go средствами стандартной библиотеки; клиент его не назначает.

Проценты вводятся точными строками и в Go переводятся в сотые процента:
«12,34» → 1234; cash_weight_units + сумма weight_units ровно 10000.
Доля денег хранится в заголовке: это одна сумма в валюте портфеля, без фиктивного
asset_id и без nullable-ключей. Строки активов могут отсутствовать при доле
денег 100%; отсутствие заголовка означает отсутствие плана.
INTEGER разрешён здесь с явно заданным масштабом; SQL SUM и REAL не используются.
Диапазон, тип и ссылки защищены БД, межстрочная сумма и формат — Go.
Валидатор и запись выполняются одним сценарием в одной транзакции; прямого
редактирования таблиц UI нет. Частично заполненный план не становится видимым.
Внешние ключи включены на каждом соединении, применяется штатная резервная
копия перед следующей версионированной миграцией. Существующие миграции неизменны.

Связь с ID актива позволяет хранить цель до первой покупки. Смена типа актива
не меняет цель. Удаление используемого актива должно отклоняться FK;
удаление справочника сейчас вне области фичи. Валюта плана берётся из портфеля,
не дублируется в строках и не задаётся клиентом.

Хранятся доли активов и денег, версия и идентичность плана; цены, количества,
целевые суммы,
сценарии покупок/продаж не сохраняются. Расчёт использует Go math/big.Rat
и согласованный снимок плана, операций, котировок, курсов и split.
Цена — более поздняя из котировки и покупки своего портфеля. В отличие от
ADR 0016 продажа в этой фиче не обновляет источник цены. Общие механизмы
выбора котировки, конвертации и split переиспользуются с явным выбором
кандидата-покупки, без изменения правил существующих обзора и анализа.
DTO процентов, денег, количеств, ID и версии — строки; number допустим только в геометрии ECharts.
Слой оценки предоставляет точные внутренние значения до округления вывода;
использовать двухзначные значения DTO текущего анализа как вход расчёта нельзя.

## Альтернативы

- JSON в portfolios проще по числу таблиц, но не даёт FK на каждый актив,
  уникальности строк и проверки диапазона отдельным ограничением.
- Только строки целей без заголовка экономят таблицу, но усложняют различение
  отсутствия плана и управление атомарной заменой/версией.
- Целевые количества/суммы устаревают после пополнений и split; проценты
  выражают устойчивое намерение пользователя.
- Глобальные доли в assets не позволяют разным портфелям иметь разные цели.
- Распределение по типам требует второго правила распределения внутри группы,
  без которого нельзя однозначно получить целевые количества отдельных активов.
- История целей с датой действия полезна для исторического анализа, но текущий
  запрос относится к сегодняшнему плану. При необходимости добавить отдельно,
  не изображая текущий план как действовавший в прошлом.

## Последствия и статус

Новая схема хранит только пользовательскую настройку; журнал и дневные остатки
не изменяются при редактировании цели. Добавлены миграция 0011 и проверки
транзакционности, ссылок, точной суммы и конфликтов версий на временной БД.
Новые библиотеки не требуются. Пользователь подтвердил целевую долю денег
и выбор между котировкой и последней покупкой по дате. Запрос на реализацию
принимает точность долей 0,01%, текущий план без истории и пропорциональное
распределение дефицитов. AllocationService и предметный расчёт находятся
в internal/valuation; хранение и Wails API — в его адаптерах. Точные количества
и стоимости истории переиспользуются до округления, правила прежнего анализа
сохранены; одна подготовка истории поддерживает явный выбор только покупок.
